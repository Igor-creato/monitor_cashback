# AGENTS.md - Price Monitor Service

## Текущий контекст проекта

Этот репозиторий предназначен для отдельного микросервиса мониторинга цен товаров. Сервис должен развиваться отдельно от WordPress-плагина `cash-back`.

- Локальный путь сервиса: `F:\cash-back\monitor_cashback`.
- GitHub repo: `Igor-creato/monitor_cashback`.
- Текущая стабильная ветка репозитория: `master`.
- Предыдущая реализация была удалена коммитом `2112d20 Remove monitor cashback module`; не считай старые файлы актуальными, даже если они всплывают в истории Git или памяти агентов.
- WordPress-плагин живет отдельно: `F:\wamp64\www\kash-back\wp-content\plugins\cash-back`.
- Инфраструктурный/deploy repo живет отдельно: `F:\cash-back\deploy`.

## Границы ответственности сервиса

Сервис мониторинга цен отвечает за backend-часть мониторинга:

- прием и нормализацию ссылок на товары;
- watchlist пользователя;
- хранение карточек товаров и истории цен;
- планирование проверок цен;
- worker/fetch pipeline;
- health/source status/quarantine;
- API для WordPress-плагина;
- будущие расширения: поиск товаров, мониторинг корзины и избранного только через согласованный официальный доступ.

WordPress-плагин отвечает за UI, личный кабинет, настройки, авторизацию пользователя, proxy/подпись запросов к сервису и интеграцию с cashback UX. Не переносить бизнес-логику WordPress-плагина внутрь сервиса без отдельного решения.

## Ветки и организация разработки

- Не писать новый функционал напрямую в `master`.
- Для нового функционала использовать ветки `feature/<short-name>`.
- Для багов использовать `fix/<short-name>`.
- В `master` допускаются только проверенные merge/fast-forward изменения после зеленых тестов, lint и security checks.
- Если bugfix нужен и в стабильной ветке, и в активной feature-ветке, перенеси его в обе ветки, чтобы контракт сервиса и интеграция с WordPress не расходились.
- Не смешивать в одном PR/коммите backend сервиса, WordPress UI и deploy-инфраструктуру, если это не один явно описанный интеграционный шаг.

## Главный принцип

Работай как осторожный senior-разработчик. Цель - минимальное, безопасное, проверяемое изменение без поломки существующего функционала.

Запрещено:

- ломать существующий рабочий функционал;
- делать скрытый рефакторинг "заодно";
- удалять или переписывать модули без явного разрешения;
- добавлять production-зависимости без согласования;
- хардкодить секреты, токены, пароли, ключи, cookies, API credentials;
- менять публичные API, REST endpoints, DB-схемы или формат данных без описания совместимости и согласования;
- коммитить код, если тесты, lint или security checks не проходят.

## Перед началом любой задачи

1. Кратко сформулируй цель задачи и Definition of Done.
2. Найди затрагиваемые файлы, классы, функции, endpoints, DB-таблицы, background jobs, queues, cron/scheduler tasks и тесты.
3. Проверь существующий код и переиспользуй его, если это возможно.
4. Не дублируй уже существующую логику. Если существующий код нужно доработать - предложи минимальное изменение.
5. Если задача может затронуть архитектуру, безопасность, внешние API, зависимости или интеграции - изучи актуальную официальную документацию.
6. Внешнее исследование и поиск open-source решений выполняй только когда это действительно нужно для задачи.
7. Перед реализацией составь короткий план: файлы, изменения, тесты, риски.

## Safe Development Workflow

Использовать для реализации, исправления или рефакторинга кода, когда нужно безопасно изменить проект с тестами, проверкой существующего кода, security review и финальной верификацией. Не использовать для простых вопросов без изменения кода.

### 1. Разбор задачи

- Переформулируй цель.
- Определи границы задачи.
- Определи, что НЕ входит в задачу.
- Сформулируй Definition of Done.
- Если задача противоречит существующей архитектуре или может сломать рабочий функционал, остановись и предложи варианты.

### 2. Исследование существующего кода

- Найди все затрагиваемые модули, классы, функции, endpoints, scheduler jobs, workers, queues, DB-таблицы и внешние контракты.
- Проверь, есть ли уже похожая логика.
- Переиспользуй существующий код вместо дублирования.
- Если дублирование кажется проще, сначала объясни почему переиспользование невозможно.

### 3. Документация и внешнее исследование

Используй внешнее исследование только если задача требует актуальных сведений:

- внешние API;
- новая библиотека;
- security-sensitive функциональность;
- архитектурное решение;
- интеграция с WordPress/WooCommerce, браузерным расширением, CPA, платежами, очередями, БД или микросервисной инфраструктурой.

При исследовании:

- предпочитай официальную документацию;
- проверяй дату актуальности;
- не используй неподдерживаемые open-source проекты;
- не добавляй зависимости без согласования.

### 4. План

Перед кодом напиши план:

- какие файлы будут изменены;
- какие тесты будут добавлены;
- какие риски есть;
- какие проверки будут запущены;
- нужны ли миграции/rollback.

### 5. Тесты перед кодом

- Для бага: добавь тест, который воспроизводит ошибку, если это возможно.
- Для новой функции: сначала добавь тесты ожидаемого поведения.
- Для рефакторинга: добавь characterization tests, если поведение недостаточно покрыто.
- Если тест до кода невозможен, объясни почему и выбери альтернативную проверку.

### 6. Реализация

- Делай минимальные изменения.
- Не меняй несвязанные файлы.
- Не делай скрытый рефакторинг.
- Не меняй публичные контракты без явного указания.
- Не добавляй новые зависимости без согласования.

### 7. Проверка качества

Запусти релевантные проверки:

- unit tests;
- integration tests;
- e2e tests, если применимо;
- lint;
- static analysis;
- type checks;
- build;
- migrations smoke/check, если затронута БД;
- security scan/secrets scan, если доступно.

Если что-то падает:

- исправь причину;
- повтори проверку;
- максимум 3 итерации на одну проблему;
- если не удается исправить, остановись и объясни причину простыми словами.

### 8. Security review

Проверь diff на:

- XSS;
- SQL injection;
- CSRF;
- SSRF;
- broken access control;
- insecure direct object reference;
- path traversal;
- hardcoded secrets;
- утечки данных в логах;
- небезопасную обработку файлов;
- небезопасные redirects;
- небезопасные внешние запросы;
- отсутствие permission/capability checks.

## Тесты

Перед изменением кода:

- для бага сначала добавь воспроизводящий failing test, если это возможно;
- для новой функции сначала добавь тесты на ожидаемое поведение;
- для рефакторинга добавь characterization tests, если поведение недостаточно покрыто.

После изменения:

- запусти релевантные unit/integration/e2e tests;
- запусти lint/static analysis/type checks, если они есть в проекте;
- все проверки должны быть зелеными;
- если проверку невозможно запустить, явно напиши причину и точную команду, которую нужно выполнить вручную.

## Безопасность

Для каждого изменения проверь:

- input validation на сервере;
- output escaping/encoding в HTML/JS/SQL/URL-контексте;
- SQL только через prepared statements/безопасные ORM-методы;
- REST endpoints имеют корректный permission/capability check;
- admin/AJAX actions защищены nonce/capability checks, если они находятся в WordPress-интеграции;
- нет CSRF, XSS, SQL injection, SSRF, path traversal, insecure deserialization;
- нет утечек персональных данных, токенов, cookies, ключей, webhook secrets;
- ошибки не раскрывают внутренние пути, SQL, stack traces, секреты;
- логи не содержат секретов и чувствительных данных;
- криптография не самописная;
- права доступа минимально необходимые;
- внешние URL проверяются allowlist/валидацией, если есть риск SSRF.

## Marketplace, cart и favorites policy

- Не хранить marketplace login/password в коде, fixtures, env examples, логах или БД без отдельного согласованного security design.
- Не собирать cookies/tokens/session data без явного согласия пользователя и отдельного approved design.
- Не реализовывать captcha bypass, fingerprint bypass, proxy evasion или обход антибот-защиты.
- Cart/favorites monitoring разрешен только через официальный API/OAuth/partner access или другой явно согласованный легальный и безопасный путь.
- Для публичного URL monitoring fail closed на captcha, auth wall, unsafe redirects, private/local IP, unsupported domain.

## Зависимости

Новые зависимости запрещены без согласования.

Если зависимость действительно нужна, сначала предоставь:

- зачем она нужна;
- почему нельзя использовать существующий код;
- стабильную актуальную версию;
- лицензию;
- активность поддержки;
- размер и влияние на проект;
- известные CVE/security issues;
- альтернативы;
- план удаления/замены, если зависимость станет неподдерживаемой.

## Работа с существующим функционалом

- Меняй только то, что относится к задаче.
- Не меняй бизнес-логику начислений, выплат, транзакций, webhook-обработки, балансов, ролей пользователей и API без отдельного подтверждения.
- Если обнаружена несвязанная ошибка или уязвимость, не исправляй ее молча. Запиши отдельным пунктом: файл, риск, предложение исправления.
- Сохраняй обратную совместимость публичных методов, REST API, cron/scheduler jobs и DB-схем.

## Миграции и данные

Если изменение затрагивает БД:

- миграция должна быть идемпотентной;
- должен быть план rollback;
- нельзя терять существующие данные;
- нельзя менять финансовые записи задним числом без audit trail;
- любые операции с балансом/начислениями должны быть атомарными и проверяемыми;
- для service-owned данных использовать явные миграции и smoke/check команду.

## Ожидаемая техническая траектория

Если нет утвержденного другого решения, ориентируйся на такую архитектуру:

- API service: Python/FastAPI.
- DB: PostgreSQL или согласованная альтернатива.
- Cache/locks/rate limits: Redis.
- Durable jobs: очередь + worker/scheduler.
- Migrations: Alembic или согласованный migration tool.
- Observability: structured logs, request/trace id, health/readiness endpoints, metrics.
- Deployment: Docker/Compose на test stage, с документированным rollback.

Не считай этот список разрешением автоматически добавлять зависимости. Перед добавлением production-зависимости все равно нужно согласование.

3. Какие файлы изменены.
4. Какие тесты добавлены/изменены.
5. Какие команды проверки запущены и их результат.
6. Какие security checks выполнены.
7. Есть ли риски, ограничения или что не удалось проверить.
8. Есть ли несвязанные проблемы, найденные по пути.

## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

- Dirty graphify-out/ files are expected after hooks or incremental updates; dirty graph files are not a reason to skip graphify. Only skip graphify if the task is about stale or incorrect graph output, or the user explicitly says not to use it.

- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
